## 1. Ограничения, из которых всё выведено

Эти ограничения заданы владельцем продукта и определяют весь дизайн. Меняется ограничение —
пересматривается план.

| Ограничение | Значение |
|---|---|
| Текущий трафик | практически ноль |
| Рынок и язык контента | английский, EU |
| Видео | лицо в кадре допустимо, но **как коолд-опен, не как основной формат** |
| Время | 10–15 часов в неделю всего |
| Распределение времени после спринта A | ~4 часа видео / ~6–8 часов код / 1 час чтение цифр |
| Медиабюджет | до €500/мес, **в резерве до гейта 4** (§7.4) |

Два следствия, которые надо держать в голове при чтении:

1. **Узкое место — распределение, а не продукт.** Продукт зрелый (§2). Строить новые фичи ради
   фич — прокрастинация.
2. **Часы — игра с нулевой суммой.** Любое «давай ещё и это» вычитается из чего-то другого.
   Поэтому у каждого пункта здесь есть цена в часах и условие входа.

### 3.1 Исправлено по ходу проектирования

**Дефект бюджетных бэндов — закрыт.** `BUDGET_BANDS` использовался и как бюджет на образ (интейк
отчёта), и как фильтр цены одной вещи (Shop a Look). Нижний бэнд `min: 200` при каталоге, где почти
всё дешевле €200, приводил к инверсии: выбор «подешевле» поднимал наверх самое дорогое.

Исправление (уже в рабочем дереве): разделены `OUTFIT_BUDGET_BANDS` и `ITEM_BUDGET_BANDS`
(`src/lib/budgets.ts`), потребители переключены, подпись в UI «Outfit budget» → «Price per piece»,
`INSPIRATION_MATCH_VERSION` поднят 10 → 11 (инвалидирует кэш результатов, посчитанных по старой
семантике), старый резолвер оставлен deprecated — устаревшие id клиента дают `{ mode: "any" }`
вместо исключения.

`ITEM_BUDGET_BANDS` — базис для пикера цены в анонимной подборке (§5).

**Побочный эффект, который стоит записать:** бамп `INSPIRATION_MATCH_VERSION` входит в
`CACHE_VERSION` роута Shop a Look, а набор рекомендаций Shop a Look нигде, кроме этого кэша, не
хранится. Значит все накопленные наборы разом перестали читаться — данные о том, что система
рекомендовала, потеряны, и механизма, который бы их сохранил, в системе нет. Это и есть мотивация
A1.1.

### 3.2 Задел (не в спринте)

**Сумма шопинг-листа не сверяется с заявленным бюджетом.** `matchShopping`
(`src/lib/data/catalog.ts:330`) и `matchLookItems` (`:802`) передают `max_price: profile.budgetEur.max`,
то есть бюджет на весь гардероб работает как потолок цены одной вещи. Инверсии здесь нет
(`isPriceInBudget` в этом пути не вызывается), но итоговый список может кратно превысить заявленный
бюджет, и каждая позиция формально «в бюджете». Дешёвое решение: считать сумму листа, показывать её
рядом с заявленным бюджетом, при перерасходе помечать позиции, которые можно отложить.

**Устаревшие кэш-блобы Shop a Look не удаляются.** Каждый бамп версии матчера оставляет предыдущее
поколение в бакете `assets` навсегда; сейчас там потенциально осадок от одиннадцати версий
`INSPIRATION_MATCH_VERSION`. Решение: чистка по префиксу при бампе либо TTL на бакете.

### A0. Предохранитель расхода — до всего остального

**Условие: ни один анонимный прогон не разрешается, пока A0 не закрыт.** Это не оптимизация и не
полировка — сейчас на проде открыт неавторизованный эндпоинт, каждый вызов которого стоит денег
(§3, пункт 2а). Формально A0 блокирует A2 и §5; фактически он нужен независимо от них, потому что
дыра уже открыта.

#### Что не так с текущим лимитером

`src/app/api/colours/route.ts:14-24` — три дефекта, не один:

1. **Память не делится между инстансами.** Это признаёт сам комментарий на строке 10 (и он же
   называет решение: «move to a durable store (Supabase/KV)»). При десяти тёплых инстансах
   фактический лимит не 6 за 10 минут, а 60.
2. **`hits` — `Map`, которая никогда не чистится.** Записи фильтруются только при обращении к своему
   же IP, чужие остаются навсегда. Медленная утечка памяти на тёплом инстансе.
3. **Квота тратится на мусорные запросы.** Лимитер стоит на строке 38, валидация тела — на 45–52.
   Запрос с битой картинкой съедает квоту реального человека, ничего не стоя в деньгах.

#### Выбор стора: Postgres, а не Upstash

Upstash Redis честнее по назначению — `@upstash/ratelimit` даёт sliding window и token bucket из
коробки, задержки подмиллисекундные. Но здесь считается один счётчик несколько раз в секунду в пике,
а разница между Redis и Postgres — единицы миллисекунд на фоне vision-вызова с `maxDuration = 60`.
Цена нового вендора: аккаунт, ключи в `env.ts`, ещё одна точка отказа и — главное — **вторая
площадка с персональными данными** (хэш IP), из-за чего GDPR-история (срок хранения, удаление,
бэкапы) размазывается по двум системам.

**Решение: Postgres, который уже есть.** Если объём когда-нибудь станет настоящим, реализация
меняется за интерфейсом `src/lib/rate-limit.ts` без правки вызовов.

#### Схема

```sql
create table if not exists public.rate_limits (
  bucket     text primary key,
  hits       integer not null default 0,
  window_end timestamptz not null
);

create index if not exists rate_limits_window_end_idx
  on public.rate_limits (window_end);

alter table public.rate_limits enable row level security;
-- политик нет: доступ только через service-role в RPC ниже
```

Атомарный инкремент — один round-trip, без read-then-write:

```sql
create or replace function public.rate_limit_hit(
  p_bucket text,
  p_limit  integer,
  p_window interval
)
returns table (allowed boolean, hit_count integer)
language plpgsql
security definer
set search_path = public
as $$
declare
  v_hits integer;
begin
  insert into public.rate_limits as r (bucket, hits, window_end)
  values (p_bucket, 1, now() + p_window)
  on conflict (bucket) do update
    set hits       = case when r.window_end <= now() then 1 else r.hits + 1 end,
        window_end = case when r.window_end <= now() then now() + p_window else r.window_end end
  returning r.hits into v_hits;

  return query select v_hits <= p_limit, v_hits;
end;
$$;
```

Свойства, на которые опирается дизайн:

- **Атомарность.** `on conflict do update` с `returning` сериализуется Postgres на уникальном
  индексе — гонки между инстансами невозможны. Это ровно то, чего не может текущий вариант.
- **Окно самоочищается.** Истёкшее окно сбрасывает счётчик в 1 при первом обращении. Cron нужен
  только для сборки мусора, не для корректности.
- **Фиксированное окно, не скользящее.** Всплеск на границе окна теоретически даёт двойной лимит —
  для операции за €0.02–0.04 это несущественно. Token bucket здесь оверинжиниринг.

#### Четыре уровня, порядок проверок

Проверки идут от дешёвых и важных к дорогим. **Валидация тела — до лимитера**, чтобы мусор не съедал
чужую квоту:

> разобрать и провалидировать тело → хэш фото и кэш → глобальный кап → IP → anon → vision-вызов

**Уровень 0 — хэш фото, до всех счётчиков.** Тот же файл → отдаём сохранённый результат: квота не
тратится, денег не стоит. В `colours/route.ts` этого нет вообще (строка 55: «analysed in-request and
never persisted»), а в Shop a Look приём уже реализован через `createHash("sha256")` — переносим.

**Уровень 1 — `colours:global:<YYYY-MM-DD>`: настоящий контроль стоимости.** Один ключ, одно число,
жёсткий кап. Считается от допустимой дневной траты: при €0.04 за прогон кап 2500 = максимум
€100/день. Именно это спасает при вирусном всплеске из §9.3, а не персональные квоты.

**Уровень 2 — `colours:ip:<hash(ip+salt)>:<час>`, щедро.** Мобильный трафик идёт через carrier NAT,
где сотни абонентов под одним адресом. Текущие 6 за 10 минут при трафике из TikTok будут рубить
живых людей пачками. Ориентир — **20–30 в час**, а не 6 в 10 минут. Соль обязательна, хранится хэш,
не сам адрес, срок хранения короткий (IP — персональные данные).

**Уровень 3 — `colours:anon:<anonId>:<день>`, вежливый лимит.** По анонимной cookie (§5.2, п. 7).
Обходится инкогнито за две секунды и не должен ничего защищать — его задача другая: это **триггер
мягкого гейта**. Превысил ~10 за день → «твоя палитра сохранена, войди, чтобы оставить её и прогнать
ещё», а не 429.

#### Fail-open или fail-closed — по-разному

Решение неочевидное и принимается осознанно:

- **Глобальный кап — fail-closed.** Postgres недоступен → не пускаем. Кап защищает деньги, и при
  неизвестном состоянии счётчика правильнее отказать.
- **IP и anon — fail-open.** Они защищают от неудобства, а не от расхода. Ронять весь бесплатный
  вход из-за недоступного счётчика хуже, чем пропустить лишние прогоны.

#### Кап — лид-магнит, а не ошибка

При достижении дневного капа **не** отдавать 429 с текстом ошибки. Отдавать: «сегодня мы на пределе
мощности — оставь email, пришлём твою палитру утром». Исчерпание превращается из потерянного
посетителя в захваченный лид, и переиспользует механизм захвата email из A2, п. 3.

#### Где живёт код

`src/lib/rate-limit.ts` — функция `checkLimit(bucket, limit, window)` над RPC, вызывается из роута.

**Не в `src/proxy.ts`** (в Next 16 это переименованная middleware; сейчас там только
`updateSession`). Причины: matcher покрывает практически весь сайт, то есть добавится обращение к БД
на каждый запрос; и проверка нужна после разбора тела, чтобы работал хэш фото.

**Сборка мусора** — в `vercel.json` уже есть cron `refresh-catalog` (03:00). Добавляется
`delete from rate_limits where window_end < now() - interval '1 day'` в существующий или соседний
cron-роут. Отдельной инфраструктуры не нужно.

**Уровень −1, если план Vercel позволяет:** правило rate limiting в Vercel Firewall на путь
`/api/colours`. Срабатывает на эдже, до вызова функции, то есть грубый флуд не тратит даже
invocation. Инструмент тупой (по IP), но бесплатный. См. §11.

#### Наблюдаемость — обязательна

Событие `rate_limited` в PostHog с указанием бакета. Без него нельзя отличить «трафика нет» от
«трафик приходит и получает отказ» — а именно эта путаница испортит чтение гейта 1. Плюс это прямая
оценка щедрости лимита по IP: если отказы приходятся на визиты без единого предыдущего события,
лимит режет живых.

#### Оценка

| Работа | Часы |
|---|---|
| Миграция + RPC | 1 |
| `rate-limit.ts` + подключение в роут, перестановка валидации вперёд | 1,5 |
| Хэш фото + кэш результата | 2 |
| Ответ-лид-магнит на капе | 1 |
| Событие `rate_limited` + чистка в cron | 0,5 |
| **Итого** | **~6** |

### A1. Событийная аналитика — сразу за предохранителем

Сейчас только `@vercel/analytics` (pageviews). Пяти цифр воронки физически не существует.

**Решение: PostHog** (free tier ~1M событий/мес). Своя таблица в Supabase дешевле по зависимостям,
но дороже по времени — воронки, ретеншн и session replay пришлось бы строить руками, а времени нет.

События:

```
colours_started        загрузил фото
colours_result         увидел палитру + подборку
affiliate_click        клик по товару в подборке   ← ветка монетизации без регистрации
signup

report_ready
report_opened          ← АКТИВАЦИЯ
pdf_downloaded         ← АКТИВАЦИЯ
tryon_generated
purchase

```

**Метрика активации — `report_opened` / `pdf_downloaded`, не `signup`.** Момент, когда человек
увидел себя. Вся оптимизация направляется туда, а не в клики.

### A1.1 Журнал рекомендаций — серверная половина аналитики

`affiliate_click` без записи о том, **что** было порекомендовано, бесполезен: вопрос «какие
рекомендации конвертируют» не имеет ответа в принципе. Поэтому журнал — не фича, а обязательная
часть A1.

**Что сохраняется сегодня** (проверено по коду):

| Данные | Где | Долговечность |
|---|---|---|
| Набор подобранных товаров по лукам отчёта | `reports.look_items` (jsonb, миграция 0006) | durable |
| Что именно примерили | `tryons.garments` (0016): `productId`, `title`, `category`, `imageUrl` | durable, со снимком существенного |
| Откуда инициирована примерка | `tryons.origin` (0030): `shop_a_look` / `catalog` | durable |
| **Набор рекомендаций Shop a Look** | только кэш-блоб `cachePath(user.id, hash, budgetKey)`, читается при `version === CACHE_VERSION` | **теряется при каждом бампе версии матчера** (§3.1) |

**Ключевое архитектурное решение: не делать кэш долговечным.** Вся работа кэша — инвалидироваться
при смене версии. Сделав его записью истины, придётся либо ломать инвалидацию, либо продолжать
терять историю. Это два объекта с разными жизненными циклами:

- **кэш** — ключ «хэш фото + бэнд», инвалидируется версией, короткая жизнь, задача — не платить
  дважды за один прогон;
- **журнал** — append-only, версия матчера это **поле, а не ключ**, не инвалидируется никогда.

**Что писать на прогон.** `user_id` или анонимный id (см. §5.2, п. 7), `created_at`, `photo_hash`
(**не фото**), версия матчера, `budget_band_id`, и снимок полей профиля, влиявших на ранжирование
(подсезон и палитра, `boldness`, gender, market/currency) — без последнего вопрос «почему оно так
подобрало» через месяц безответен. Далее распознанные вижном garments (garment, colour, category,
clause) и по каждому слоту ранжированные кандидаты: `product_id`, позиция, `score`, `colorScore`,
был ли это пик реранкера, флаг `outside` (вне бэнда). По каждому кандидату — **снимок
существенного** (title, цена на тот момент, image, deeplink, brand): голый FK сгниёт, поскольку
`0006_product_provenance.sql` добавил скрытие товаров, а цены меняются. Поверх — события: что
кликнули, что примерили.

**Зачем, кроме атрибуции:**

1. **Настройка матчера из анекдота в данные.** `INSPIRATION_MATCH_VERSION` = 11, каждая ревизия
   вызвана тем, что подбор выглядел неправильно (см. комментарии `catalog.ts:855-862`). С
   сохранёнными входами v12 прогоняется по входам v11 и сравнивается дифом; без них каждая ревизия
   судится по нескольким свежим прогонам на глаз.
2. **Отрицательный сигнал сейчас выбрасывается целиком.** На слот показывается
   `INSPIRATION_CANDIDATES_PER_SLOT` кандидатов, примеряют один → остальные отказы. Это тот сигнал,
   на котором учат реранкинг, и сегодня он не существует даже в запрашиваемом виде.
3. **Посев для wardrobe-as-asset.** Той фиче нужна история показанного и выбранного.

**Три обязательных условия:**

- **GDPR.** Новая таблица с пользовательскими данными обязана попасть в `/api/account/export` и в
  путь удаления аккаунта. В `llms.txt` заявлено «GDPR-first, фото приватны» — расхождение здесь
  дороже самой функции. Хранится хэш фото, не фото.
- **Срок хранения назначается сразу** (ориентир — 12 месяцев), иначе это неограниченно растущая
  таблица без заявленной цели, а GDPR срок хранения и так требует назвать. См. §11.
- **Анонимный путь** требует идентификатора — §5.2, п. 7.

**Оценка:** 5–7 часов (таблица + запись при прогоне + два события). Пользовательский UI «мои
подборки» — отдельная фича, вне спринта.

## 5. Анонимная подборка товаров

Расширение бесплатного входа: помимо палитры аноним видит **набор реальных товаров в своих цветах**,
с фильтрами по цене и поводу. Try-on закрыт регистрацией.

**Обоснование.** Палитра — коммодити: бесплатный colour-анализ есть у десятка приложений и в
TikTok-фильтрах. Палитра + покупабельная подборка в своих цветах и своём бюджете — этого не даёт
никто. Плюс: wow-момент переезжает раньше воронки, просьба зарегистрироваться становится осмысленной
(«примерь это на себе» вместо «зарегистрируйся ради отчёта»), и появляется **вторая ветка
монетизации** — affiliate-клик анонима, который никогда не зарегистрируется.

### 5.1 Почему это дешевле, чем кажется

Почти всё написано:

- `src/lib/look-contexts.ts` — таксономия поводов (`work`, `smart_casual`, `weekend`, `dinner`,
  `formal`, `travel`).
- `src/lib/budgets.ts` — `ITEM_BUDGET_BANDS` (до €50 / €50–150 / €150–400 / €400+).
- `matchInspirationItems()` (`src/lib/data/catalog.ts:959`) — эмбеддинги по слотам →
  `match_product_offers` → реранк → цветовой гейт → мягкий фолбэк при тонком инвентаре. Пайплайн v11.

Новый код — тонкий адаптер «анонимный профиль» (палитра из colour-анализа + мужской пол + бэнд +
повод) на входе существующего матчера. **10–14 часов.**

### 5.2 Обязательные решения по дизайну

1. **Показать, потом фильтровать.** Пикеры до результата — это форма перед ценностью и главный
   источник отвала на холодном трафике. Правильно: загрузил фото → **сразу** палитра + подборка по
   дефолту (smart casual, средний бэнд, валюта из гео — `src/lib/geo.ts` это умеет) → фильтры
   появляются **под** результатом. Каждое переключение фильтра — дополнительное событие вовлечения.
2. **Слово «кредиты» анониму не показывать.** «Зарегистрируйся и получи 6 бесплатных кредитов»
   требует выучить внутреннюю единицу учёта в момент максимального интереса. Должно быть:
   **«Примерить на себе — бесплатно»**. Кредиты видны уже внутри аккаунта.
3. **Фотографию донести до регистрации.** Try-on без фото невозможен, а сейчас в конце colour-флоу
   написано, что фото не сохранили. Если после регистрации просят загрузить заново — обещание
   «примерь» превращается в «начни сначала». Решение: держать фото на время сессии с **явным
   согласием**, с правкой `src/lib/privacy-content.ts` и `terms-content.ts`. Это работа с
   приватностью, а не строчка кода; альтернатива — смириться с повторной загрузкой.
4. **Граница с платным тиром.** Бесплатно отдаём **вещи**. Платно — **объяснение и себя в них**:
   почему именно это, волосы, силуэт, пропорции, 9 образов на своём теле, капсульная матрица, PDF.
   Значит в бесплатной подборке **сознательно нет** объяснений, капсульной логики и рассуждений о
   посадке. Ограничение зафиксировано здесь, иначе уползёт.
5. **Проверка покрытия каталога перед запуском.** 12 подсезонов × 6 поводов × 4 бэнда — если на
   какой-то комбинации найдётся три вещи, испорчено первое впечатление. Мягкий фолбэк матчера
   спасает частично. Один раз прогнать распределение по каталогу и **скрыть комбинации с тонким
   инвентарём**, а не показывать пустоту. Тот же запрос используется в §7.3.
6. **Таксономию не расширять.** Из первоначального списка: «походный» не заводить — технического
   outdoor в каталоге нет, подборка выйдет пустой; «экспериментальный» — это не повод, а ось
   смелости, и она уже есть отдельным параметром (`profile.boldness`). Берём шесть существующих
   контекстов + смелость отдельным переключателем.
7. **Анонимный идентификатор для атрибуции.** У анонимного прогона нет `user_id`, а ветка A
   монетизации (§9.1) — это именно анонимный click-out. Без сессионного идентификатора главная
   метрика бесплатного уровня несчитаема, а журнал рекомендаций (A1.1) не с чем связать.
   Проектируется вместе с подборкой, не после: нужен непривязанный к личности id (cookie или
   localStorage), который переносится на `user_id` при регистрации — тогда путь «аноним посмотрел →
   зарегистрировался → купил» склеивается в одну воронку. Идентификатор попадает под те же правила
   приватности, что и остальное (A1.1). Именно cookie/localStorage, **не фингерпринт** — §5.3.
8. **Что сохраняется за анонимом.** Палитра, подобранный лук и хэш фото — против анонимного id; при
   регистрации переезжают на `user_id`. Механика уже отработана в проекте на
   `PENDING_PROMO_COOKIE`: ставится до регистрации (`login/page.tsx:20`), читается в
   `auth/callback/route.ts:65` и `login/actions.ts:39`, переносится через `applyWelcomeCredits`,
   удаляется после использования. Переиспользуем этот паттерн, а не изобретаем.

### 5.3 Фингерпринт и «один прогон на человека» — рассмотрено и отклонено

Обсуждалось: снимать браузерный фингерпринт, чтобы каждый аноним мог сгенерировать палитру и
подборку **ровно один раз**. Отклонено по трём независимым причинам. Записано, чтобы предложение не
вернулось без аргументов.

**1. Точность фингерпринта хуже всего именно на нашем трафике.** Профиль ошибок обратный нужному.
Ложный пропуск (упрямый получил второй прогон) стоит €0.02. Ложное срабатывание (настоящий новый
посетитель получил отказ) стоит визита на самом верху воронки. А трафик планируется из TikTok и
Reels, то есть почти целиком мобильный — худший случай: два iPhone одной модели с одной версией iOS
дают почти идентичный отпечаток, коллизии не гипотетические. Итог: холодный посетитель на первом в
жизни визите видит «вы уже использовали бесплатный анализ», что читается как сломанный сайт или
обман. Плюс Safari (ITP) и Firefox (ETP) снижают энтропию отпечатка — точность будет только падать.

**2. Юридически это жёсткое ограничение, а не мягкое.** Фингерпринтинг для идентификации попадает
под ePrivacy Art. 5(3) наравне с cookie; позиция EDPB по device fingerprinting требует **согласия**,
если это не строго необходимо для запрошенной услуги. «Ограничить бесплатный тир» — коммерческая
цель, не техническая необходимость, исключение не применяется. Значит согласие берётся **до**
фингерпринта, то есть **до** бесплатного инструмента — а это форма перед ценностью, ровно то, что
§5.2 п. 1 запрещает как главный источник отвала. Отдельно: в `llms.txt` заявлено «GDPR-first, фото
приватны»; скрытый фингерпринт ради отказа в услуге — противоположная интонация и реальная
экспозиция на EU-рынке.

**3. Экономика не оправдывает.** Прогон стоит €0.01–0.04 (§9.3). Правило экономит центы и платит
конверсией на входе, попутно ломая три работающие вещи: существующую кнопку «Try another photo»
(`reset()` в `ColoursExperience.tsx`) — а второе фото это признак вовлечения, не абьюза; ветку A
монетизации (§9.1), где аноним без регистрации приносит affiliate-доход; и собственный конвейер
контента (§6) вместе с UGC-форматом «пришли своё фото», где прогон многих фотографий — рабочий
процесс.

**Что вместо.** Четыре слоя A0 плюс мягкий гейт: хэш фото (повтор бесплатен), глобальный дневной кап
(реальный контроль расхода), щедрый лимит по IP, вежливый лимит по анонимной cookie как триггер
предложения зарегистрироваться. Персональной квоты «один прогон» нет. Настоящий риск — не любопытный
человек с тремя фотографиями, а автоматизированный абьюз объёмом и вирусный всплеск, и против них
работает кап, а не квота.

**Если решение когда-нибудь пересмотрят**, минимальные условия: порог заметно больше единицы (~3),
обязательный escape hatch («это не я / начать заново»), согласие до снятия отпечатка и замер доли
отказов, приходящихся на визиты без единого предыдущего события — это прямая оценка ложных
срабатываний.

### 5.4 Объединение с Shop a Look

Анонимная подборка — это **Shop a Look, развёрнутый наоборот**: там на входе фото образа, здесь фото
лица, дальше один и тот же пайплайн. При этом Shop a Look сейчас закрыт авторизацией
(`api/shop-a-look/route.ts:61` → 401) без содержательной причины.

**Решение: одна анонимная поверхность с двумя входами** — «твоё лицо → твои цвета + подборка» и
«фото любого образа → он же в твоих цветах». Оба заканчиваются одним закрытым try-on. Одна
реализация, два хука для видео, два кластера SEO, одна воронка.

## 6. Контент-движок

**Принцип: движок — это код, а не рабочий процесс.** При 4 часах в неделю ролики нельзя монтировать
руками. Генератор из готового отчёта выдаёт готовый к постингу вертикальный MP4; человеческий вклад
— выбор материала и озвучка.

Прецедент в репозитории уже есть: `scripts/generate-investor-pptx.mjs` + `npm run deck:pptx` локально
собирает медиа-артефакт из данных.

### 6.1 Форматы по убыванию силы

1. **Правильная палитра против неправильной** на одном человеке. Уже стоит на главной
   (`ImageComparisonSlider`). Самый арестующий визуал продукта и лучше всего размножается:
   12 подсезонов × формат = минимум 12 роликов, каждый бьёт в самоидентифицирующуюся аудиторию.
2. **Before/after try-on на реальном человеке.** «Без лица» не значит «без людей»: субъект —
   присланная пользователем фотография. Самый сильный движок, потому что бесконечный и каждый
   участник сам разносит результат.
3. **Капсульная математика** — 5 вещей → 4 образа, правило 60/30/10 в движении.
4. **Пролистывание PDF-журнала** — скринкаст, жанр satisfying-контента.

### 6.2 Трек без лица — дефолт

Развести два независимых решения: **без лица ≠ без голоса.**

| Вариант | Оценка |
|---|---|
| Только текст на экране | Дешевле всего, потолок вовлечения низкий |
| **Твой голос без лица** | **Дефолт.** ~90% выигрыша в доверии при ~20% затрат и нулевой публичной экспозиции |
| TTS голосом Carlo | Бренд-консистентно (Carlo — открыто заявленная персона), масштабируется, но узнаваемо синтетический — режет доверие там, где мы его строим |

### 6.3 Трек с лицом — надстройка, не альтернатива

Лицо = **коолд-опен 3–5 секунд**, тело ролика — тот же сгенерированный материал. Генератор получает
дополнительный входной слот; раз в месяц отснимаются 10 универсальных открытий одним батчем за
полчаса («я инженер, одеваюсь как инженер», «я отдал гардероб AI-стилисту на неделю», «мне прислали
вот эту фотографию»), они переиспользуются между десятками роликов. Цена — ~30 минут в неделю.

**Роль на камере: не эксперт, а объект.** Эксперт по стилю отпадает — нет бэкграунда, аудитория
считает подделку за неделю. Основатель-строитель собирает build-in-public аудиторию разработчиков —
это не ICP. Остаётся «подопытный»: требований к экспертизе ноль, аутентичность максимальная, и это
ровно то, что продукт производит.

### 6.4 Как выбирается трек — замером, не спором

Генератор строится один, сразу с опциональным слотом под коолд-опен. Затем 10 роликов без лица с
голосом и 10 тех же форматов с пятисекундным лицом. Сравниваются удержание на 3-й секунде и переходы
на `/colours`. Это гейт 2 (§9.4), а не предпочтение.

### 6.5 Техническая реализация

**Remotion** — React рендерится в MP4 покадрово: `useCurrentFrame()`, `interpolate()`, `spring()`,
таймлайн через `<Sequence>`; headless Chrome снимает кадры, ffmpeg кодирует. Это не слайдшоу, а
настоящая анимация на 30 fps — всё, что умеет браузер, становится видео.

Движение из статики без единого сгенерированного кадра: Ken Burns, маскированный вайп между before и
after, выкладка свотчей пружиной, параллакс, кинетическая типографика.

**Пайплайн — голос первым, таймлайн из голоса.** Это ключевое решение, оно и убирает монтаж:

1. Дубль в один заход → `take1.mp3`.
2. Локальный Whisper (`@remotion/install-whisper-cpp`) → JSON с таймингами каждого слова.
3. Композиция читает JSON: субтитры подсвечиваются слово за словом (`@remotion/captions`), склейки
   сцен привязаны к ключевым словам.
4. `<Audio src={staticFile("take1.mp3")} />`.

Перезаписал дубль → одна команда → готовый ролик с синхронными субтитрами и склейками. **Монтажа
нет.**

**Б-роллы** поддерживаются нативно: `<OffthreadVideo>` кладёт MP4 внутрь композиции, React-графика
поверх. Тот же механизм принимает коолд-опен с лицом — это просто первый `<Sequence>`.

Структура:

```
remotion/
  Root.tsx                    регистрация композиций
  compositions/
    PaletteReveal.tsx         подсезон → палитра → реплика Carlo
    BeforeAfter.tsx           маскированный вайп между двумя фото
    CapsuleMath.tsx           5 вещей → 4 образа
  components/
    Captions.tsx              субтитры из word-timings
    ColdOpen.tsx              опциональный слот под клип с лицом
    EndCard.tsx               valetti.fit
  data/<slug>.json            палитра, ссылки на изображения, тайминги
scripts/
  video-data.mjs              Supabase по report id → data JSON
  video-voice.mjs             whisper по mp3 → word timings
```

```bash
npm run video:data -- <reportId> && npm run video:voice -- take1.mp3 && npm run video:render -- PaletteReveal
```

Рендерить **локально**, не на Vercel (лимиты по времени выполнения). 45 секунд = 1350 кадров;
на M-серии с параллелизмом — минуты, не часы.

**Переиспользование существующего кода — с оговоркой.** `src/lib/og/report-share-card.tsx`
рендерится через `ImageResponse` из `next/og`, то есть satori: поддерживается подмножество CSS
(только flexbox, без grid, инлайновые стили). Remotion крутит настоящий Chrome и умеет всё. Значит
компоненты один-в-один не переносятся, но переносятся брендовые токены (`INK`, `PAPER`, `CREAM`,
`BRASS` уже вынесены константами), шрифты из `assets/fonts/`, логика палитры из
`src/lib/colour-palette.ts` и вся выборка данных. Ограничения снимаются, а не добавляются.

**Лицензия Remotion** — порог по размеру компании; условия проверить **до** вложения 8–10 часов в
композиции. Фолбэк: ffmpeg по отрендеренным PNG-кадрам — бесплатно, дольше в разработке, Ken Burns и
вайпы выражаются фильтрами ffmpeg вместо CSS.

### 6.6 ИИ-генерация видео — не в первой фазе

Главное визуальное преимущество — реальное before/after на реальном человеке, реальная палитра,
реальные страницы журнала. Такого материала нет ни у кого в нише. Сгенерированный б-ролл «мужчина
идёт по улице в закатном свете» — то, чем набит каждый faceless-аккаунт: читается как филлер и
обесценивает кадр.

Где ИИ-видео добавляет: establishing shot под настроение, которого продукт не производит (осенняя
берлинская улица под «Berlin autumn palette») — 1–2 секунды, стоит денег за клип, nice-to-have.
Заводить после того, как форматы устоятся, и только если замер покажет прирост удержания.

**Отдельно исключено:** анимация фотографии реального пользователя в видео — дрейф идентичности,
высокая стоимость и снова вопрос согласия на анимацию чужого лица.

### 6.7 Каналы распространения

TikTok, IG Reels, YT Shorts — один ассет во все три, кросс-постинг на таком объёме нормален.
Реалистичная частота — **4–5 роликов в неделю**.

**Pinterest — добавлен, в `growth-plan.md` его нет.** Это поисковик по образам, контент только
изображения, пины компаундятся годами, мужской стиль покрыт заметно хуже женского. Для продукта,
который уже производит красивые картинки, это самый дешёвый канал: ассеты сгенерированы для видео,
публикация — почти нулевые дополнительные затраты.

### 6.8 Музыка — трейд-офф, который надо принять осознанно

**Закадровый голос и трендовый звук взаимоисключающи.** Трендовое аудио даёт бонус к охвату, но
перекрывает озвучку. Ставка на голос ⇒ трендовый звук из стратегии выпадает, под голос кладётся
тихая лицензионная подложка (Epidemic Sound и аналоги, ~€10–15/мес). Плюс: один файл льётся на
YouTube и Pinterest, чего с трендовым аудио нельзя.

### 6.9 Юридические ограничения

1. **UGC требует явного согласия.** Присланные фотографии в публичных роликах — галочка согласия при
   отправке + хранение факта согласия. Чужое лицо в рекламе без него — GDPR и права на изображение.
2. **Try-on на знаменитостях запрещён.** Самый заманчивый формат по просмотрам и единственный, который
   приносит cease-and-desist или бан платформы (право на публичность и изображение). Разборы образов
   — можно; генерация «одел знаменитость в нашу капсулу» — нет.

### 6.10 Недельный ритм

| Работа | Время |
|---|---|
| Отобрать материал 3 отчётов + запустить генератор | 30 мин |
| Озвучка 4–5 роликов | 40 мин |
| Постинг в 3 платформы + Pinterest | 40 мин |
| Комментарии | 30 мин |
| **Итого** | **~2,5 часа** |

Остаток бюджета видео — на подтяжку форматов, которые залетели.

## 7. Программатик-SEO

### 7.1 Два принципа

1. **Не делать крестовое произведение.** 12 × 6 × 4 = 288 страниц одной командой — форма, которую
   Google классифицирует как doorway pages. На домене без внешних ссылок это даёт не трафик, а
   песочницу на весь сайт.
2. **Программатик-страницы не зарабатывают ссылки.** Они ранжируются только при каком-то авторитете
   домена. Значит нужна горстка ссылко-притягивающих активов — сам бесплатный инструмент, демо-отчёт,
   несколько настоящих статей — и они линкуются внутрь кластера. Это и есть настоящая причина держать
   первую волну маленькой.

### 7.2 Волна 1 — 12 страниц подсезонов (уже написаны)

`src/app/colours/[subseason]/page.tsx` существует: метаданные, canonical, OG-картинка через
`/api/og/colours/[subseason]`. Подсезоны — `src/lib/style-profile.ts:25` (`deep-winter` …
`deep-autumn`), палитры — `src/lib/colour-palette.ts`. Не хватает: родитель `/colours` отдаёт 404,
страниц нет в `sitemap.ts`, не упомянуты в `llms.txt`. Всё три закрываются в §A2.

Интент — самый ценный в нише: «am I a soft autumn», «deep winter palette male», «cool winter colors
men». Colour-анализ в поиске почти целиком женский; «men» делает запрос малоконкурентным при живом
спросе.

**Улучшение, превращающее шаблон в уникальный контент:** живая подборка реальных товаров каталога в
этой палитре — настоящие цены и картинки, меняются с инвентарём. Страница перестаёт быть текстом, у
которого поменяли прилагательные.

Выпустить 12, дать проиндексироваться, посмотреть реальные позиции. Только потом расширяться.

### 7.3 Волна 2 — подсезон × повод

`/colours/[subseason]/[occasion]` на существующих `LOOK_CONTEXTS`. Интент: «smart casual outfits for
soft autumn men», «what to wear to a wedding warm spring».

**Тот же генератор, что и анонимная подборка (§5)**: страница — статически отрендеренный результат
матчера для канонической комбинации. Одна реализация, две поверхности, обе улучшаются одной правкой.

**Предохранитель:** страница не генерируется и не попадает в sitemap, если инвентаря по комбинации
мало (тот же запрос покрытия из §5.2). Тонкая страница хуже отсутствующей. Из 72 ожидаемо выживет
40–55 — `formal` и `travel` по редким подсезонам вряд ли наберут товар.

### 7.4 Волна 3 — настоящие статьи, ради ссылок

5–8 текстов руками, не генерацией: как одеваться при невысоком росте, при плотном телосложении, при
широких плечах (типы фигуры заданы в `BodyTypePicker`), мужская капсула на 10 вещей, разбор правила
60/30/10. Высокочастотные и для мужчин недообслуженные запросы (есть в `growth-plan.md` §B).

Задача двойная: трафик по информационным запросам **и** ссылки, которые программатик-кластер получить
не может, с передачей веса внутрь кластера через внутренние ссылки.

### 7.5 Чего не делать — с причинами

| Не делаем | Причина |
|---|---|
| Товарные страницы `/catalog/[slug]` | Affiliate-страницы с описаниями из фида — самая наказуемая категория. Работают только с реальной добавленной ценностью (каким подсезонам вещь идёт, с чем носить). Плюс текучий инвентарь → тысячи мёртвых страниц. После появления авторитета и с дисциплиной по 404/410 |
| Профессия × город | 7 × 47 = 329 страниц с почти идентичным контентом. Это спам, отфильтруют. Позже — несколько городских страниц руками |
| Мультиязычность | hreflang, дубли, тонкие переводы на домене без авторитета. Английский кластер сначала должен доказать, что ранжируется. Немецкий как первый нон-англ — отдельный проект с локализацией всего сайта |

### 7.6 Технический чеклист

- **`sitemap.ts` сделать динамическим** — сейчас захардкоженный массив из 8 записей; строить из
  таксономии, отфильтрованной по покрытию инвентарём.
- **`generateStaticParams`** для страниц подсезонов; **ISR** для всего инвентарь-зависимого, иначе
  цены в выдаче устареют.
- **Canonical при query-параметрах.** `/colours/[subseason]` принимает `?u=` и `?c=`, меняющие
  OG-картинку; canonical уже собирается как `absoluteUrl('/colours/${subseason}')` без параметров —
  правильно, но при добавлении фильтров легко сломать. Зафиксировано.
- **JSON-LD** — `Article` + `ItemList` для подборки; образец в `src/components/DemoReportJsonLd.tsx`.
- **Внутренняя перелинковка:** подсезон → дочерние поводы → бесплатный инструмент → демо-отчёт.
  Программатик-кластеры без этого умирают.
- **Image SEO.** `/api/og/colours/[subseason]` рендерит карточку палитры — топливо для Pinterest и
  результат в поиске по картинкам («soft autumn palette men»). Один уже написанный эндпоинт
  обслуживает два канала.

### 7.7 AI-поиск

`src/lib/llms-txt.ts` уже собирает документ по llmstxt.org с явными инструкциями для краулеров
(включая «не индексировать приватные отчёты, публичен только демо-слаг») — аккуратнее, чем у
большинства. Доля переходов из AI-ответов по информационным запросам уже сопоставима с классической
выдачей, а «какой у меня цветотип» — ровно такой запрос. Значит `llms.txt` расширяется вместе с
кластером: раздел с 12 подсезонами и бесплатным инструментом. Дешевле любой другой SEO-работы и почти
никем не делается.

### 7.8 Ожидания по срокам

Домен молодой, ссылок нет. Индексация — недели. Первый осмысленный органический трафик — 2–4 месяца.
Заметный — 6+. Поэтому SEO идёт **параллельно** видео, а не вместо: видео даёт трафик сейчас и первые
ссылки, SEO забирает его к концу полугодия. Ждать результата от SEO внутри 90 дней — значит бросить
его на третьем месяце, ровно перед тем, как он начнёт работать.

## 8. B2B: магазины, бутики, ателье

**Возражение, с которого надо начинать: B2B — это другая компания.** Другая механика продаж, другой
продукт (мультитенантность, места сотрудников, чужой инвентарь), другой денежный цикл. При 10–15
часах в неделю и нулевом B2C открыть второй фронт — способ получить два недостроенных бизнеса.
Поэтому формы отсортированы по цене входа, а не по привлекательности.

**Момент, определяющий порядок: конфликт интересов.** Бутик не отправит своего клиента в инструмент,
который порекомендует ему Zara. Сегодня каталог — Zara, Reserved, Massimo Dutti, M&S. Для магазина со
стоком Valetti конкурент, а не сервис. У барбершопов, салонов и груминга этого конфликта **нет** —
только та же аудитория. Значит первыми идут партнёры без конфликта.

### 8.1 Форма 1 — партнёр раздаёт бесплатный анализ ✅ в 90 дней

Барбершопы, салоны, груминг, шоурумы без своего стока. QR на зеркале, карточка в чеке.

Инфраструктура стоит: `src/lib/promotions.ts` (`generatePromoCode`, `createPromotion`,
`redeemPromotion`), админка `PromoAdminPanel.tsx`, `/api/promo/redeem`. Не хватает **атрибуции по
партнёру** в отчётности.

Партнёру: бесплатный сервис для клиента, повод взять контакт, отличие от соседей. Тебе: самая целевая
офлайн-аудитория — мужчина, который уже платит за то, чтобы лучше выглядеть, и сидит в кресле полчаса.

Это B2B как **канал**, а не продуктовая линия. Работы ~6 часов (атрибуция + одностраничник для
партнёра). Условие входа: спринт A завершён — раздавать ссылку на страницу, отдающую 404, бессмысленно.

### 8.2 Форма 2 — бутик отдаёт инвентарь ✅ после 90 дней, как продуктовая задача

`scripts/feeds/sources.mjs` уже содержит адаптер **`gmc`** (Google Merchant / Shopping XML) с полным
маппингом: `g:brand`, `g:color`, `g:gender`, `g:price`, `g:availability`, `g:link`, изображения.
**Любой магазин на Shopify отдаёт этот формат штатно** — подключение бутика это вставить URL фида.
Инженерных затрат ноль.

Оправдано даже если ни один бутик не заплатит: бренд обещает quiet luxury без логотипов, а каталог
предлагает Zara — прямое противоречие, подтачивающее главное обещание. Независимые бутики и малые
бренды — ровно тот инвентарь, который обещанию соответствует.

Оффер: бесплатное размещение + квалифицированный трафик (покупатель, которому сток подходит по
колориту). Rev-share позже, на старте ничего.

**Жёсткий фильтр на входе: только те, у кого есть Shopify или готовый фид.** У независимых плохие
данные — нет структурных размеров, нет остатков, часто нет e-commerce; ручная работа на каждого не
масштабируется и в 8 часов кода в неделю не влезает.

### 8.3 Форма 3 — white-label в магазине ⛔ не сейчас

Уже публично обещано на `/pricing`: «Business · white-label — Generate reports under your own salon
or studio brand, with your catalogue as the product source. In development — get in touch to pilot»,
с ценой «from …». При этом «get in touch» ведёт в mailto футера — ни формы, ни учёта заявок.

Суть: планшет в магазине, продавец прогоняет клиента, отчёт рекомендует **только сток этого
магазина**. Поднимает чек, даёт сервис, который магазин сам не построит, и повод взять контакты
клиента. €50–200/мес или по цене за отчёт. Самая высокая выручка на аккаунт.

Почему не сейчас — причина не техническая. **Первый вопрос магазина: «сколько мужчин вы уже одели»,
и сегодня честный ответ — «почти никого».** Платный B2B заблокирован разговором, а не принципом: без
кейсов не продаётся ни за какие деньги. Бесплатная раздача (форма 1) не заблокирована, потому что там
ты даёшь, а не просишь.

### 8.4 Форма 4 — ателье 🔶 оппортунистический тест

У ателье нет каталога — они шьют, значит товарная половина продукта не нужна. Нужен **бриф по
клиенту**: подсезон, палитра, контраст, силуэт, пропорции, цвета тканей, подкладок и рубашек. Портной
силён в конструкции и обычно слаб в колористике — это ровно та дырка, которую Valetti закрывает.

Продукт — один PDF-бриф; `src/lib/pdf/` и `colour-palette.ts` дают почти всё, товарную часть надо
выключить. €5–15 за бриф или маленькое месячное место. Минус: рынок маленький, продажа поштучная,
масштабирования нет. Делать, если ателье само проявит интерес; специально не охотиться.

### 8.5 Форма 5 — подарочные ваучеры через магазины ⛔ декабрь

Магазин продаёт ваучер на кассе, делим маржу. Ждёт подарочной механики.

### 8.6 Дешёвая проверка спроса — на этой же неделе

На `/pricing` висит обещание white-label с ценой, а инбаунда нет — только mailto. Поставить `/business`
с внятным описанием и формой из трёх полей (тип бизнеса, город, есть ли онлайн-каталог) — **час
работы**. Дальше два месяца смотреть, приходит ли спрос. Приходит — есть список пилотов до первой
строчки мультитенантности. Не приходит — сэкономлен месяц разработки на догадке.

## 9. Метрики, гейты, 90 дней

### 9.1 Воронка

```
посетитель → загрузил фото → увидел палитру + подборку
                                    ├─→ affiliate_click — доход без регистрации
                                    └─→ регистрация → отчёт → открыл отчёт/PDF → покупка → повтор
```

Левая ветка — новая и её обычно не считают: аноним, который никогда не зарегистрируется, всё равно
может принести деньги. Поэтому `affiliate_click` — событие первого класса.

### 9.2 Целевые значения

Расхождение с `growth-plan.md` §6: там «free → signup ≥ 40%». Это нереально для холодного анонимного
трафика и **опасно** — при нормальных 8% будет вывод «всё сломано» и начнётся починка работающего.

| Шаг | Метрика | Реалистично | Отлично |
|---|---|---|---|
| ToFu | визит → загрузил фото | 10–20% | >25% |
| Технический | загрузил → увидел результат | >95% | — |
| Ветка A | результат → `affiliate_click` | 10–25% | — |
| Ветка B | результат → регистрация | **5–15%** | >15% |
| Путь | регистрация → отчёт сгенерирован | 50–70% | — |
| **Активация** | отчёт сгенерирован → открыт / PDF | >80% с письмом | — |
| Монетизация | активация → первая покупка | 3–8% | >8% |
| Повтор | покупатели с ≥2 покупками за 90д | 15–25% | — |

Загрузка селфи — высокое трение, и не техническое, а психологическое: люди боятся отдавать лицо.
Поэтому 10–20% на входе честнее 25–35%.

Разрыв «с письмом / без письма» в активации — это цена пункта A3. Оценочно теряется около трети
сгенерированных отчётов. Единственная метрика, где одно письмо даёт двузначный прирост.

### 9.3 Экономика бесплатного уровня

База — `docs/referer.md` (1 кредит ≈ €1, COGS Basic ≈ €0.34, Premium ≈ €1.08). Новая строка:

**Анонимный прогон** = vision-вызов по картинке, сжатой до 768px (`ColoursExperience.tsx`,
`MAX_EDGE = 768`) + эмбеддинги по слотам + векторный поиск ≈ **€0.01–0.04**.

- 1 000 прогонов/мес → €10–40. Не проблема.
- 100 000 прогонов/мес (вирусное попадание, которое мы и планируем) → **€1 000–4 000** без единой
  регистрации. Отсюда обязательность лимитера и дневного капа (§4, A2).

Встречная сторона, арифметика прикидочная, допущения явные: click-out 15%, конверсия у ритейлера 3%,
средний чек €80, комиссия 6,5% → **≈ €23 с 1 000 прогонов** против €10–40 затрат. То есть бесплатный
уровень **примерно самофинансируется**, но только если `affiliate_click` размечен и атрибуция
работает. Проверить на первой тысяче прогонов, не на десятой.

### 9.4 Гейты

Недели у гейтов — **ориентиры**. Гейт срабатывает по завершении предшествующей работы, а не по
календарю: сдвинулся спринт A — сдвинулись все следующие. Сроки в §9.5 даны от нижней границы
оценки.

**Гейт 1 — конец спринта A (недели 3–4).**
Проверка: пять цифр существуют; анонимный поток доходит до результата >95%; письмо о готовом отчёте
приходит; лимитер держит.
Не пройден → **каналы не открываются, ни одного ролика.** Лить трафик в неизмеримую воронку — потерять
и трафик, и возможность научиться.

**Гейт 2 — недели 6–7 (после ~20 роликов и волны 1 SEO).**
Измеряем: удержание на 3-й секунде по форматам; лицо против без лица; визит → загрузка фото.
- Хотя бы один формат даёт заметные просмотры → удваиваем его, перестаём распылять.
- Все 20 ровные, медиана ниже пары сотен просмотров → **проблема в хуке, а не в частоте.** Не
  выпускать ещё 20 таких же: менять формат целиком либо признать, что канал не идёт. Критерий
  остановки записан заранее намеренно — в моменте всегда кажется, что нужно «ещё немного».

**Гейт 3 — недели 8–9.**
Измеряем: результат → регистрация.
- <5% → сломан момент просьбы, а не трафик. Чинить формулировку и место до любых денег на трафик.
- >10% → воронка здоровая, готовим платный.

**Гейт 4 — недели 11–12, разблокировка €500.**
Два условия одновременно: есть формат с доказанным удержанием (станет креативом) и накоплена
аудитория для ретаргетинга.
Тратить **только на ретаргетинг тех, кто сделал бесплатный анализ и не зарегистрировался** — самый
дешёвый и тёплый сегмент. Холодный prospecting при €500/мес даёт не статистику, а счёт.

**Гейт 5 — неделя 12.**
LTV/CAC по каналам. Масштабируем только >3. Остальное **останавливаем**, а не «дорабатываем».

**Разблокировка рефералки и подарков** — по условию, не по дате: **первые 20 платящих.**

### 9.5 90 дней

| Недели | Содержание |
|---|---|
| **1–4** | **Неделя 1 начинается с A0 — предохранителя расхода; до его закрытия анонимный доступ не включается.** Далее спринт A целиком (§4 + §5), включая журнал рекомендаций (A1.1). Волна 1 SEO: 12 страниц подсезонов в `sitemap.ts` и `llms.txt`. Трафика нет — это нормально. Гейт 1 |
| **5–7** | Композиции Remotion + пайплайн голос → тайминги → рендер. 20 роликов: 10 без лица с голосом, 10 с коолд-опеном. Pinterest теми же ассетами. Гейт 2 |
| **8–10** | Удваиваем победивший формат. Волна 2 SEO (40–55 страниц). 10 офлайн-партнёров с промо-кодами (форма 1). Гейт 3 |
| **11–12** | Ретаргетинг на €500. Волна 3 SEO — 5–8 статей ради ссылок. 3–5 бутиков на Shopify через `gmc` (форма 2). Гейты 4 и 5 |

### 9.6 Недельный ритм (после спринта A)

| Работа | Время |
|---|---|
| Видео (§6.10) | 4 ч |
| Код (SEO-волны, затем то, что покажут цифры) | 6–8 ч |
| **Чтение цифр** | **1 ч** |

Последняя строка выписана отдельно намеренно: без неё она не происходит никогда, а вся конструкция
гейтов держится на ней.

### 9.7 Ветка на случай неудачи

Если к концу 90 дней трафик близок к нулю, ни один формат не зашёл и платящих единицы — честный
вывод: **клин выбран неверно, а не усилий было мало.** Варианты в порядке предпочтения:

1. **Сузиться до одного триггера — свадьбы.** Максимальная срочность, готовность платить и явная
   дата. «Что надеть на свадьбу» ищут с деньгами в руках, в отличие от «как одеваться лучше».
2. **Уйти в B2B white-label (форма 3).** К этому моменту появятся первые кейсы, что снимает главное
   возражение магазина. Чек на аккаунт кратно выше, клиентов нужно кратно меньше.
3. **Сменить покупателя на подарочный сегмент.** Женщина, покупающая отчёт партнёру — другой человек,
   другая мотивация, другие каналы. Продукт тот же, маркетинг полностью другой.

Записано заранее, чтобы на четвёртом месяце не шлифовать мёртвый клин из инерции.

## 10. Область действия и декомпозиция

Этот документ — **стратегический дизайн, а не один план реализации.** Он покрывает несколько
независимо поставляемых потоков работ, и попытка исполнить его одним планом провалится.

Порядок планов реализации:

0. **A0 — предохранитель расхода** (§4, A0). Не поток работ, а предусловие: закрывает уже открытый
   на проде платный эндпоинт (§3, пункт 2а). Делается первым, отдельно от всего, ~6 часов.
1. **Спринт A + анонимная подборка** (§4, §5) — первый настоящий план, за который стоит браться
   после A0. Всё остальное заблокировано гейтом 1.
2. **Контент-движок** (§6) — после гейта 1.
3. **SEO-волна 2** (§7) — после гейта 2, использует генератор из §5.
4. **Партнёрская раздача** (§8, форма 1) — после гейта 1, независимо от 2 и 3.

Остальное (формы 2–5, товарные страницы, мультиязычность, рефералка, подарки, wardrobe-as-asset,
мембершип) — вне 90 дней, с зафиксированными выше условиями входа.

## 11. Открытые вопросы

Требуют решения до или во время реализации. Ни один не блокирует старт спринта A — но вопросы 7 и 8
касаются A0 и решаются до включения анонимного доступа.

1. **Лицензия Remotion** — проверить актуальные условия до вложения часов в композиции (§6.5).
2. **Согласие на хранение фото между анонимным флоу и регистрацией** — держать сессионно с явным
   согласием (правки `privacy-content.ts`, `terms-content.ts`) либо смириться с повторной загрузкой
   (§5.2, п. 3).
3. **Фактическая стоимость одного анонимного прогона** — замерить на первой сотне и подставить в
   расчёт §9.3; от неё зависит величина дневного капа.
4. **Покрытие каталога** по (подсезон × повод × бэнд) — прогнать один раз, результат определяет и
   набор фильтров в §5, и набор страниц волны 2 в §7.
5. **Срок хранения журнала рекомендаций** — ориентир 12 месяцев; решается до первой записи, потому
   что попадает в политику приватности и в GDPR-обоснование (A1.1).
6. **Форма анонимного идентификатора** — cookie или localStorage, и как он склеивается с `user_id`
   при регистрации, не ломая ветку A атрибуции (§5.2, п. 7).
7. **Тариф Vercel** — доступно ли rate limiting в Vercel Firewall на текущем плане. Если да,
   уровень −1 в A0 ставится первым, до всякого кода: он отсекает грубый флуд на эдже, не тратя даже
   invocation.
8. **Величина дневного капа** — считается от допустимой траты: кап = €/день ÷ стоимость прогона.
   Зависит от открытого вопроса 3 и назначается до включения анонимного доступа, а не после.
