# Гардероб как актив — план реализации (Valetti)

Фича: пользователь фотографирует (или импортирует) одежду, которая у него уже есть → Valetti собирает структурированный, эмбеддированный «свой гардероб» → каждый отчёт, шопинг-лист и лук становятся **gap-driven** («это у тебя уже есть; купи эти 3 вещи и откроешь 6 новых образов»), а не общим списком покупок.

> **Правки от 2026-08-03.** Шесть изменений относительно черновика от 2026-07-15 — главное: основной
> путь наполнения теперь **«Это моё» из каталога, а не загрузка фото**, поэтому Phase 1 можно выкатить
> вообще без vision-пайплайна. Каждая правка помечена ⚠️ в тексте. Обоснование и очерёдность связаны с
> `docs/superpowers/specs/2026-08-01-valetti-growth-design.md`.

**Зачем эта фича (продуктовая логика)**
- Удержание: одноразовый отчёт превращается в живой профиль, к которому возвращаются.
- ⚠️ **Исправлен конкурентный тезис.** В исходном черновике было «ни у кого из конкурентов этого нет».
  Это уже не так: **TryDrobe — цифровой гардероб с виртуальной примеркой**, плюс целая категория
  closet-приложений (Pureple, Nouva, Dressly и другие — см. `docs/growth-plan.md` §1.1). Дифференциатор
  не сам гардероб: closet-приложения *организуют то, что есть, и собирают из этого образы*, и ни одно
  не продаёт недостающую вещь с объяснением «почему». Stitch Fix продаёт, но не знает твой шкаф;
  Zalando знает только свой каталог. **Бесспорно именно сочетание: gap-driven советы о покупке,
  опирающиеся на профиль цвета/посадки и шопабельный каталог.** Позиционировать и ценить против этого,
  а не против тезиса «у нас есть фича гардероба».
- Доверие: «не покупай то, что уже есть» — самый сильный proof обещания бренда «метод, а не мнение».
- Ров: данные гардероба накапливаются — стоимость переключения растёт с каждой добавленной вещью.
- Монетизация: делает осмысленным запланированный membership за €14.99/мес (ежемесячный «Carlo's edit»
  из *твоего* гардероба + свежий каталог) и создаёт новый платный артефакт (Wardrobe Audit).

## 1. UX-потоки

### 1.1 Страница гардероба — `/wardrobe`
Новая top-level страница рядом с `/reports`, `/gallery`, `/photos` (навигация: «My wardrobe»).

⚠️ **Сначала прочитай §1.2 — приоритет путей наполнения изменился.** Загрузка фото больше не основной
путь; основной — вещи из каталога. Сама страница та же, но в Phase 1 рисуются только
карточки из каталога, а загрузка фото появляется в Phase 2.

- **Пакетная загрузка** (drag & drop, камера телефона): фото вещи плашмя, на вешалке или на человеке. Для MVP — одна вещь на фото (валидируется, см. §5).
- Каждая загрузка → распознавание (§3) → **карточка вещи**: изображение, автозаполненные название, категория, чип(ы) цвета + цветовое семейство, формальность, сезон, бейдж «palette fit» (✓ в твоей палитре / ✕ вне палитры — считается по цветовому сезону из последнего отчёта).
- Все автозаполненные поля **редактируемые** (распознавание иногда ошибается; правка пользователя — бесплатная разметка для нас).
- Фильтры: категория, цветовое семейство, palette-fit, источник.
- Действия с вещью: примерить (1 cr — ⚠️ **с гейтом, см. ниже**), архивировать («отдано / износилось»), удалить.

⚠️ **Примерка с фото из гардероба не заработает так, как было написано изначально.** `runTryOn` принимает
`garmentImageUrl` (`src/lib/ai/tryon.ts:262`) и **не знает, что на картинке**, а снимок вещи на человеке
или на вешалке в плохом свете даёт плохой рендер — переносится вещь *плюс* чужое тело или кривой
силуэт. Фото гардероба по определению хуже каталожных. Формулировка §5 «вещи на человеке — ок»
относится только к *распознаванию*.

Гейт: примерка доступна для **вещей из каталога** (настоящая предметная съёмка) и, для вещей из фото,
только если классификатор типа кадра говорит, что вещь снята плашмя/чисто — тот же классификатор,
что в growth spec §8.3 gate 4; его стоит сделать один раз и переиспользовать в трёх местах
(B2C-примерка каталога, гардероб, B2B-тенанты). Иначе действие лучше спрятать, чем брать кредит
за плохой рендер.

### 1.2 Пути наполнения — ⚠️ приоритет перевёрнут

Черновик от 2026-07-15 делал загрузку фото основным путём, остальное — довеском. Это наоборот, и это
главный риск внедрения в плане: **никто не фотографирует сорок вещей по одной.** Пользователь загрузит
пять, увидит, что полезный gap-анализ ещё далеко, и не вернётся. А вещь из каталога приходит бесплатно
и без ошибок: название, категория, цвет, эмбеддинг **и нормальное товарное фото**.

Новый приоритет:

1. **«Это моё»** на любом товаре каталога, на строках шопинг-листа прошлых отчётов и в истории примерок
   → создаёт вещь гардероба, связанную с `product_id`. Без фото, **без vision-вызова, без ошибки
   распознавания, без правок пользователя**. Примерка работает, потому что картинка — настоящая
   предметная съёмка.
2. **Цикл после покупки**: после клика «Shop →» по аффилиату при следующем визите тихий вопрос
   «Купил {title}? Добавить в гардероб» (на клиенте, из истории кликов; трекинг заказов не нужен).
   Это момент с самым высоким интентом в продукте, и инструментировать его ничего не стоит —
   `affiliate_click` уже есть в таблице событий (growth spec, A1).
3. **Загрузка фото** — запасной путь для того, чего нет в каталоге. Всё ещё нужна (большая часть
   реального гардероба появилась до любого каталога), но это Phase 2, не Phase 1.

**Следствие для MVP: Phase 1 вообще не нужен AI-пайплайн.** Всё из §3 — vision-вызов, durable-воркфлоу
распознавания, нормализация категории/цвета, обработка ошибок, цикл «правка → пересчёт» — уезжает
в Phase 2. Это снимает большую часть исходной оценки Phase 1 и большую часть её риска: остаётся
CRUD плюс векторный запрос.

### 1.3 Gap-экран — экран, который приносит деньги (`/wardrobe` → вкладка «Coverage»)
- **Матрица покрытия капсулы**: детерминированный капсульный blueprint профиля (уже считает `capsuleMatrix` в `src/lib/style-extras.ts`) как слоты; в каждом слоте — своя вещь, которая его закрывает, или «нет» с лучшим матчем из каталога.
- Главная цифра: «У тебя 7 из 12 капсульных вещей → +3 вещи откроют 9 новых образов.»
- **Outfit-unlock score** на каждую предложенную покупку: сколько новых комбинаций на неделю она открывает вместе с уже имеющимися вещами (§4.3).

### 1.4 Интеграция в отчёт (где ценность становится видимой)
- **Шопинг-лист**: вещи, которые уже есть (или есть близкий аналог), получают бейдж «IN YOUR WARDROBE ✓» вместо ссылки на покупку; список переранжируется так, чтобы сначала закрывать *дыры*.
- **Луки**: заземление промпта, чтобы минимум один лук в отчёте был «собирается из гардероба + 1 новая вещь» (явно подписан).
- **Новая секция отчёта «Your wardrobe»** (Lookbook+): вердикты keep / tailor / retire по своим вещам, флаги вне палитры, дубликаты («у тебя 4 почти одинаковых navy-джемпера»).
- **Стартовый визард**: опциональный шаг 2.5 «Добавь текущий гардероб» (можно пропустить, с пометкой «сделаешь позже на /wardrobe») — **не** делать блокирующим; визард и так на пределе длины.

## 2. Модель данных

Новая миграция `00xx_wardrobe.sql`:

```sql
create table if not exists public.wardrobe_items (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users (id) on delete cascade,
  source text not null default 'photo',      -- photo | catalog | tryon | manual
  product_id uuid references public.products (id) on delete set null,
  photo_path text,                            -- key in 'photos' bucket (null for catalog-sourced)
  title text not null,
  category text not null,                     -- same taxonomy as products.category
  subcategory text,
  color text,                                 -- primary color name
  color_hex text,
  color_family text,                          -- same families as scripts/feeds/color.mjs
  attrs jsonb not null default '{}',          -- pattern, fabric, formality, season, fit, condition
  palette_fit text,                           -- 'in' | 'near' | 'off' (vs user colour season)
  status text not null default 'active',      -- active | archived
  embedding vector(1536),                     -- same space as products.embedding
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index if not exists wardrobe_items_user_idx on public.wardrobe_items (user_id, status);
create index if not exists wardrobe_items_embedding_idx
  on public.wardrobe_items using hnsw (embedding vector_cosine_ops);
```

- RLS: select/insert/update/delete только у владельца (как политики `photos`).
- RPC `match_wardrobe_items(user_id, query_embedding, threshold, count)` — та же форма, что `match_product_offers`; нужна для проверки «уже есть что-то похожее?» при матчинге шопинга.
- **Та же модель эмбеддингов и то же векторное пространство, что у `products`** (`openai/text-embedding-3-small`, 1536) — ключевое решение: свои вещи и товары каталога сравниваются напрямую по cosine similarity, поэтому gap-анализ — это векторный запрос, а не отдельный матчер.
- GDPR: включить `wardrobe_items` в `/api/account/export`; каскадное удаление уже закрыто `on delete cascade`; фото идут в существующий бакет `photos`, так что текущий поток удаления их покрывает.

## 3. AI-пайплайн — распознавание вещи

Новый `src/lib/ai/wardrobe.ts`:

1. **`recognizeGarment(photoUrl)`** — один vision-вызов (`modelVision`, claude-sonnet-4.5) со схемой Zod `Output.object` (тот же паттерн, что `analyzeProfile` в `src/lib/ai/pipeline.ts`):
   ```
   { isGarment: boolean, itemCount: number, title, category, subcategory,
     colors: [{name, hex}], pattern, fabricGuess, formality (1-5),
     seasons: [...], condition: 'good'|'worn'|'unclear' }
   ```
   - `isGarment=false` или `itemCount>1` → отказ с понятным текстом («одна вещь на фото») — это же гейт качества фото.
   - Нормализовать `category`/`color_family` через существующие классификаторы (regex категорий в `scripts/feeds/normalize.mjs`, `scripts/feeds/color.mjs`) — вынести две чистые функции в `src/lib/`, чтобы скрипты инжеста и приложение ими делились (сейчас они только на стороне скриптов).
2. **Эмбеддинг**: собрать ту же форму строки `embedText`, что у товаров (title + category + color + attrs) → `embed()` → сохранить.
3. **`paletteFit(item, profile)`** — детерминированно, без LLM: color_family против палитры цветового сезона пользователя (переиспользовать таблицы палитр в `src/lib/style-extras.ts`).
4. Пакетный поток: загрузки ставят durable workflow (`src/workflows/recognize-wardrobe.ts`, тот же паттерн `"use workflow"`/`"use step"`, что `refresh-catalog.ts`), чтобы дамп из 30 фото не упирался в таймауты serverless; вещи появляются на странице постепенно (поллинг, как у `ReportReadyNotifier`).

Заметка по COGS: распознавание — один небольшой vision-вызов (доли цента) — достаточно дёшево, чтобы быть бесплатным; **в этом пайплайне нет генерации картинок**, линия image (72% COGS) не трогается.

## 4. Gap-анализ и интеграция в отчёт

### 4.1 Детекция «уже есть похожее» (шопинг-лист)
В `matchShopping` / `matchLookItems` (`src/lib/data/catalog.ts`): после выбора кандидатов для каждого кандидата вызвать `match_wardrobe_items` с эмбеддингом кандидата; если cosine sim ≥ ~0.80 **и** та же категория **и** то же цветовое семейство → пометить `ownedSimilar: {wardrobeItemId, title}` на `ShoppingItem`. Рендер показывает бейдж и убирает ссылку на покупку; вещь уходит вниз своей категории. Порог подкрутить на своём гардеробе до релиза (см. валидацию §7).

### 4.2 Gap-driven переранжирование
Слоты капсульного blueprint (из `capsuleMatrix`) минус покрытие своими вещами = **gap-слоты**. `matchShopping` получает аргумент `gapSlots` и бустит кандидатов, которые закрывают пустой слот. Выбор «hero piece» предпочитает вещь с максимальным рычагом среди *дыр* — это чинит текущую слабость (hero piece = случайный INVEST).

### 4.3 Outfit-unlock score
Детерминированно, переиспользует правила пар на неделю из `style-extras.ts`: для кандидата посчитать валидные комбинации (формальность + совместимость цветовых семейств, уже закодированные там) со своими вещами. Показывать как «открывает N образов» на gap-вещах — это самый убедительный аргумент купить, который продукт может сделать, и это чистый TypeScript, ноль стоимости AI.

### 4.4 Заземление промпта отчёта
`executeReportGeneration`: сериализовать компактное саммари гардероба (топ ~40 активных вещей: title/category/color/formality — несколько сотен токенов) в промпт `recommend` с инструкциями: не советовать покупать почти-дубликаты; собрать ≥1 лук в основном из своих вещей; в do/don't ссылаться на свои вещи по имени, где уместно. Саммари также кладётся в снимок `reports.intake`, чтобы старые отчёты оставались воспроизводимыми.

### 4.5 Секция Wardrobe Audit (платная)
Новая опциональная секция, только если в гардеробе ≥ ~8 вещей: LLM-проход по саммари гардероба + профилю → keep / tailor / retire с причинами, кластеры дубликатов (попарный embedding sim), список вне палитры. Рендерится как секция отчёта между Capsule и Shopping. Переводится существующим путём `translateReportParts` для не-EN отчётов.

## 5. Ограничения и крайние случаи

- **Одна вещь на фото** (MVP) — enforced через `itemCount` из распознавания; нарезка нескольких вещей на одном кадре — приятность phase-3.
- **Человек на фото**: вещи на человеке — нормально (распознавание это умеет), но на кадре может быть лицо → хранить в том же бакете `photos` с согласием; загрузки в гардероб **не** требуют biometric consent по Art. 9, потому что человека мы не анализируем — вместо этого одна строка уточнения в Privacy.
- **Ошибки распознавания**: всё редактируемо; правка пересчитывает embedding + palette_fit (дёшево).
- **Абьюз/стоимость**: ⚠️ **не строить второй лимитер.** В growth spec A0 уже есть durable
  атомарный лимитер (`public.rate_limits` + RPC `rate_limit_hit`) с глобальным дневным потолком трат
  и схемой fail-closed/fail-open. Распознавание гардероба становится ещё одним бакетом
  (`wardrobe:user:<id>:<day>`) на том же механизме, и его прогоны считаются в тот же глобальный кап.
  Только vision, в худшем случае копейки — смысл переиспользовать A0 в том, чтобы был одно место,
  которое отвечает «сколько мы сегодня потратили».
- ⚠️ **Разрешение картинок и объём хранения — в исходном черновике этого не было, а это станет самой
  большой статьёй storage в продукте.** Пятьдесят вещей по 3–8 МБ — это 150–400 МБ *на пользователя*.
  В отличие от §5.2 п. 3 growth spec — где исходное селфи надо хранить, потому что оно кормит примерку
  человека, — фото гардероба в оригинале не нужно: распознаванию хватает ~1024px, а примерке вещи
  (где она вообще разрешена, см. §1.1) — ~1280–1600px. **Даунскейлить на клиенте при загрузке**, как
  уже делает `ColoursExperience.tsx` через `MAX_EDGE`; это примерно на порядок меньше счёта.
  Вещи из каталога картинку не хранят — ссылаются на `products.image_url`.
- **Холодный старт**: gap-экран нуждается в отчёте (профиль/капсула). Без него страница гардероба всё равно работает (загрузка, карточки без палитры) и показывает «Собери отчёт, чтобы увидеть дыры» — новая поверхность конверсии в визард.
- **Устаревший профиль**: если пользователь пересобирает отчёт, бейджи palette_fit лениво пересчитываются по самому новому профилю.

## 7. Фазы и оценки

⚠️ **Перефазировано, и у каждой фазы теперь есть условие входа — в исходном черновике их не было.**
Гардероб — механика удержания, а удержанию нужны существующие пользователи. По growth spec это вне
90-дневного плана; эти условия как раз определяют, когда начинать.

**Phase 0 — Гардероб только из каталога (дни, не недели)**
Миграция + RLS/RPC; страница `/wardrobe` рисует **только карточки из каталога**; «Это моё» в
каталоге, на шопинг-строках прошлых отчётов и в истории примерок; бейдж palette-fit; `match_wardrobe_items`.
Без vision-пайплайна (§1.2). Примерка разрешена — это товарные фото.
**Условие входа: ≥20 пользователей владеют отчётом.** Gap-анализу нужны профиль и капсульный blueprint —
заметка про холодный старт в §5 честна, поэтому до этого порога фиче нечего сказать.
*Ship gate: на своём аккаунте отметка 10 своих вещей заметно меняет шопинг-лист следующего отчёта.*

**Phase 1 — Gap-движок в отчётах (~2 недели)**
Бейджи «уже есть похожее» в шопинге; gap-переранжирование + фикс hero-piece; вкладка coverage с матрицей капсулы +
outfit-unlock scores; саммари гардероба в промпте отчёта; шаг визарда 2.5 (можно пропустить).
**Условие входа: Phase 0 показывает, что люди реально отмечают своё** — цель ≥30% владельцев отчёта
отмечают ≥3 вещи за две недели. Если нет, у gap-анализа нет входа, и загрузка фото это не спасёт.

**Phase 2 — Наполнение с фото (~2 недели)**
Всё из §3: воркфлоу распознавания, нормализация, редактируемые поля, классификатор типа кадра для
гейта примерки, политика даунскейла (§5).
**Условие входа: Phase 1 дала измеримый рост shopping-CTR на gap-ранжированных строках.** Только тогда
стоит платить за vision и UX ошибок распознавания.
*Ship gate (как в исходном черновике): распознать 20 реальных фото вещей с ≥80% верных
category+colour без правок.*

**Phase 3 — Петли удержания (~1–2 недели, можно отставать)**
Платная секция Wardrobe Audit; кластеры дубликатов; ежемесячный edit для membership (всё равно
заблокирован до выкладки payments/membership).

Зависимости: Phases 1–2 не зависят от платежей (unlock аудита в Phase 3 имеет смысл только при живом чекауте). Главная неопределённость — модель/промпт распознавания: затаймбоксить 1-дневный спайк на 30 разных фото (плашмя / на вешалке / на человеке / плохой свет), прежде чем фиксировать схему `attrs`.

## 8. Метрики успеха

⚠️ **Выражать их именами событий в существующей таблице `public.events`** (growth spec, A1) — не как
отдельную систему метрик. Иначе появятся два места, которые не согласятся об одном числе.

| Метрика | События | Цель |
|---|---|---|
| Активация | `wardrobe_item_added` на пользователя, группировка | ≥30% владельцев отчёта с ≥3 вещами за 2 недели (вход Phase 0 → Phase 1) |
| Микс наполнения | `wardrobe_item_added` с `props.source` = `catalog` / `tryon` / `post_purchase` / `photo` | должны доминировать каталожные пути; если доминирует `photo`, инверсия §1.2 была неверной и её надо пересмотреть |
| Удержание | повторные визиты, пользователи гардероба vs остальные | ≥2× 30-дневный возврат |
| Аплифт отчёта | конверсия во 2-й отчёт / апгрейд тира | — |
| Shopping CTR | `affiliate_click` на gap-ранжированных строках vs база | измеримый аплифт = вход в Phase 2 |
| Качество распознавания (только Phase 2) | `wardrobe_item_edited` / `wardrobe_item_added` | доля правок <30% |

Строка про микс наполнения — та, за которой смотреть жёстче всего: это прямой тест правки §1.2,
и читать её дёшево.

## 9. Явно вне скоупа (пока)

- Нарезка нескольких вещей с одного фото; трекинг носки / cost-per-wear; outfit дня с учётом погоды; социальный шаринг гардероба; интеграции перепродажи/донации. Всё правдоподобно позже; ничего из этого не нужно, чтобы доказать петлю.
