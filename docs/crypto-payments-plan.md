# Оплата кредитов криптовалютой — план реализации (Valetti)

**Ответ на «возможно ли»: да, и это одна из самых дешёвых по трудозатратам интеграций.** Платёжный слой уже построен как «провайдер + вебхук → начисление кредитов», крипта встаёт третьим провайдером без переделки логики кредитов.

---

## 1. Почему это ложится в текущую архитектуру

Сейчас (проверено по коду):

- `env.paymentProvider` выбирает `stripe | lemon_squeezy`, мастер-выключатель — `PAYMENTS_ENABLED`.
- `/api/checkout` принимает `packageId`, находит пакет в `CREDIT_PACKAGES` и возвращает URL хостед-чекаута, прокидывая `userId` + `credits` в custom data.
- Вебхук (`/api/lemon-squeezy/webhook`) проверяет подпись → читает `custom_data` → вызывает
  `grantCreditsExternal(admin, { userId, amount, reason, refExt: "ls_<orderId>" })`.
- `grantCreditsExternal` **идемпотентен**: уникальный `ref_ext` в `credits_ledger` + RPC `grant_credits_ext`.

Крипто-платёж — ровно та же форма: хостед-инвойс → вебхук со статусом → `grantCreditsExternal` с `refExt: "np_<paymentId>"`. **Логику кредитов трогать не нужно вообще.**

## 2. Выбор провайдера (ключевое требование — деньги на свой кошелёк)

Требование «зачисление на свой криптокошелёк» отсекает кастодиальные решения (Stripe crypto, биржевые Pay-сервисы), где средства оседают на счёте провайдера/биржи.

| Вариант | Некастодиальность | Комиссия | Ops | Комментарий |
|---|---|---|---|---|
| **NOWPayments** | да — форвардит на твой адрес | ~0.5–1% | низкий | Хостед-инвойсы, IPN-вебхуки с HMAC, 100+ монет. **Рекомендую для старта** |
| **BTCPay Server** | полная (свой xpub) | 0% | высокий | Свой сервер; максимум контроля, но это инфраструктура на поддержке |
| **OpenNode** | частично | ~1% | низкий | BTC/Lightning, отличный UX для мелких сумм |
| Coinbase Commerce | зависит от режима | ~1% | низкий | Модель менялась в сторону кастодиальной — проверять текущие условия |

**Рекомендация: NOWPayments** — некастодиальный форвардинг на твой кошелёк, хостед-страница оплаты (не нужно рисовать QR и следить за сетями), вебхуки с подписью. Если позже захочется 0% и полного контроля — BTCPay ставится как второй провайдер по тому же интерфейсу.

**Важно по монетам:** дефолтом ставить **стейблкоины на дешёвой сети**. При покупке пакета за €10 комиссия сети Ethereum (ERC-20) может съесть половину платежа, а волатильность BTC за 15 минут инвойса — реальный риск для маржи.

### USDT и MiCA — обязательно учесть (ЕС)

С **1 июля 2026** MiCA-лицензированные биржи в ЕЭЗ делистили **USDT**: Tether не получил авторизацию e-money token. Держать USDT физлицам не запрещено, но **регулируемые площадки ЕС не могут его листить для клиентов ЕС**.

Что это значит для нас (бизнес в Чехии):

- **Принимать USDT можно** — процессоры и кошельки его поддерживают, пользователи его любят (особенно TRC-20).
- **Проблема не в приёме, а в выводе**: конвертировать выручку USDT → EUR через регулируемые ЕС-площадки станет неудобно.
- **USDC и EURC — MiCA-совместимы** (у Circle есть EMI-лицензия), они остались на европейских листингах и конвертируются в EUR без трений.

**Практическое решение:** разделить «чем платит клиент» и «в чём получаем мы». Процессоры позволяют задать payout-валюту отдельно:

| Клиент платит | Мы получаем на кошелёк |
|---|---|
| USDT (TRC-20), USDC, BTC, ETH… | **USDC** (или EUR) |

Так пользователю остаётся привычный USDT, а на нашей стороне оседает совместимый актив, который чисто уходит в EUR.

### Сети (важнее самой монеты)

| Сеть | Комиссия | Вердикт для пакетов €10–79 |
|---|---|---|
| **TRC-20 (Tron)** | ~$1 | Основная для USDT в мире — включить |
| **Polygon / Base / Arbitrum** | центы | Включить, лучший вариант для USDC |
| **BSC, TON, Solana** | центы | Можно включить |
| **ERC-20 (Ethereum)** | $2–20+ | **Выключить или предупреждать** — съедает маржу на мелких пакетах |

## 3. Поток оплаты

1. На `/pricing` рядом с «Buy credits» появляется вторая кнопка — **«Pay with crypto»**.
2. `POST /api/checkout` с `{ packageId, provider: "crypto" }` → создаём инвойс у провайдера с `order_id = <наш paymentId>`, суммой **в EUR** (провайдер сам конвертирует в выбранную монету по курсу на момент оплаты) и `success_url`/`ipn_callback_url`.
3. Пользователь уходит на хостед-страницу, выбирает монету/сеть, платит.
4. Провайдер шлёт IPN на `/api/crypto/webhook` по мере смены статусов: `waiting → confirming → confirmed → finished` (или `partially_paid`, `expired`, `failed`).
5. **Кредиты начисляем только на `finished`** (средства подтверждены и отправлены на твой кошелёк), идемпотентно по `refExt`.
6. Пользователь возвращается на страницу «Payment pending» → фронт поллит статус → как только кредиты начислены, показываем баланс.

Отличие от карты: платёж **не мгновенный** (минуты). Нужен экран ожидания, а не сразу «спасибо».

### Зачем отдельная таблица `crypto_payments`

`credits_ledger.ref_ext` достаточно для идемпотентности, но не для UX и сверки. Нужна связка «инвойс → пользователь → пакет → статус»:

```sql
create table public.crypto_payments (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users (id) on delete cascade,
  provider text not null default 'nowpayments',
  invoice_id text not null unique,      -- id платежа у провайдера
  package_id text not null,
  credits int not null,
  amount_eur numeric not null,          -- фиксируем EUR-цену на момент создания
  pay_currency text,                    -- напр. 'usdcbase'
  pay_amount numeric,                   -- сколько монеты просили
  status text not null default 'waiting',
  tx_hash text,
  amount_eur_received numeric,          -- для бухгалтерии: EUR-эквивалент на момент зачисления
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

RLS: владелец видит только свои строки; пишет только service-role (вебхук).

## 5. Крайние случаи (их надо решить заранее)

| Случай | Решение |
|---|---|
| **Недоплата** (`partially_paid`) | Кредиты не начислять. Показать «доплатите X» либо начислить пропорционально — решить политикой; я бы не начислял и просил доплату |
| **Переплата** | Начислить пакет, разницу оставить как бонусные кредиты (проще, чем возврат в крипте) |
| **Истёк инвойс** | Статус `expired`, кредиты не начисляются, пользователь создаёт новый |
| **Платёж после истечения** | Провайдер всё равно шлёт IPN — обработать и начислить (деньги-то пришли) |
| **Волатильность** | Инвойс фиксирует курс на 15–20 минут; для маржи безопаснее стейблкоины |
| **Возвраты** | Крипта необратима. В ToS — «crypto payments are final, no refunds». Плюс: **нет chargeback'ов** |
| **Дубли IPN** | Уже закрыто `refExt` + unique-индексом на `ref_ext` |
| **IPN не дошёл** | Крон-сверка: раз в час опрашивать статусы всех `crypto_payments` в статусе `waiting/confirming` старше 20 минут |
| **Неверная сеть** | Провайдер решает это на своей стороне — ещё один аргумент против самописного приёма на адрес |

## 6. Юридическое и налоговое (не пропустить)

**Самое важное последствие, которое легко упустить:** Lemon Squeezy сейчас работает как **merchant of record** и берёт на себя НДС по всем продажам в ЕС. Крипто-процессор этого **не делает** — он просто передаёт деньги. Значит по крипто-продажам:

- НДС на цифровые услуги в ЕС (OSS/MOSS) становится **твоей обязанностью** — по месту нахождения покупателя;
- нужно фиксировать **EUR-эквивалент на момент получения** каждого платежа (поле `amount_eur_received`) — это база для учёта;
- удержание крипты на кошельке порождает курсовые разницы, которые тоже учитываются;
- при заметных объёмах появляются AML/KYC-вопросы — их закрывает выбор регулируемого процессора (ещё аргумент против приёма «напрямую на адрес» без посредника).

Это не блокер, но перед включением стоит согласовать с бухгалтером — иначе крипто-выручка окажется в серой зоне на фоне аккуратного LS-учёта.

## 7. Порядок реализации

**Фаза 1 — бэкенд (пол дня).**
1. Аккаунт NOWPayments, указать адрес кошелька (лучше отдельный для бизнеса), получить API key + IPN secret.
2. `crypto-pay.ts` + миграция `crypto_payments`.
3. `/api/crypto/webhook` + ветка в `/api/checkout`.
4. Тест на testnet/sandbox провайдера + маленький реальный платёж (€10 в USDC).

**Фаза 2 — UI (полдня).**
5. Кнопка «Pay with crypto» на `/pricing`, экран ожидания с поллингом, состояние «pending» в `/account` → Credits.

**Фаза 3 — надёжность (пара часов).**
6. Крон-сверка зависших платежей.
7. Алерты на `partially_paid` / `failed` (в тот же канал, что и прочие warning'и).

**Фаза 4 — учёт.**
8. Экспорт крипто-платежей в CSV для бухгалтерии (EUR-эквивалент, дата, tx hash).

## 8. Стоит ли вообще

**За:** ниже комиссии, чем у карт (0.5–1% против ~3–5% + fees LS), нет chargeback'ов, доступ для пользователей без карт/из регионов с проблемным эквайрингом, и это в духе продукта (техно-аудитория 25–45).

**Против:** усложняется учёт (см. §6), появляется ручная работа с волатильностью и кошельком, а доля крипто-платежей в подобных B2C-продуктах обычно **1–5%** от оборота.

**Мой вывод:** делать имеет смысл, но как **дополнительный** способ оплаты рядом с картами, а не вместо. Трудозатраты около дня — оправданы. Только не включать до разговора с бухгалтером про НДС, потому что смена merchant of record — единственная реально рискованная часть, и она не техническая.
